# Design

## Context

参见 `proposal.md - Why`。设计只依赖以下现状约束：

- 执行侧消息序列由 `render_node` 一次构造：`[system] + [history] + [其余模板消息]`，模板未引用输入时再追加一条用户消息。`history` 来自会话检查点，`system` 每轮重新渲染、不累积。
- Prompt 渲染器是**严格闭合**的：模板里的占位符必须先在 `variables` 声明，传入未声明变量即 422；变量类型仅标量；模板产不出 `tool` 角色消息。
- 模型工具卡由 `model_tool_bindings` 从快照的 `spec` 构造，当前只读 `spec.description` 与 `spec.input_schema`。
- 工具执行层已把异常分类为稳定错误码（`INPUT_INVALID`、`TOOL_TIMEOUT`、`TOOL_HTTP_ERROR`、`TOOL_MCP_ERROR`、`TOOL_OUTPUT_INVALID`、`RESOURCE_UNAVAILABLE`、`HIGH_RISK_BLOCKED`），但适配层把异常压成 `content + error_code`，节点层见 `ok=False` 即抛错终止。
- `ValidationFailedError` 的字段路径与原因存放在 `details`，`message` 只是类默认文案。
- Agent 版本快照为不可变 JSON，`config_hash` 由快照内容计算；发布记录引用快照，不随上游资源变化。

## Goals / Non-Goals

**Goals:**

- 模型能从工具卡本身获得构造参数所需的全部信息：用途、参数含义、取值格式、结果语义。
- 工具失败成为一次可消费的交互，而不是一次执行的终点；纠错成本从「整轮重来」降到「一个回合」。
- 运行时事实（当前时间、时区）成为版本级显式依赖，可审计、可回放、不可被调用方伪造。
- 「模型收到了什么」在轨迹里可直接复核，不需要读代码反推。

**Non-Goals:**

- 不做平台侧自然语言日期归一化（不把「明天」在网关翻译成日期）。本期把当前时间作为事实交给模型，由模型自行换算；换算不可靠时由参数校验与错误回灌兜底。
- 不引入用户身份、地理位置、页面上下文等其它运行时事实。本期只落地 `now` 与 `timezone`，机制留出扩展位。
- 不自动回写远端 `MCP` 服务的参数描述，补全只发生在平台侧的工具版本上。
- 不改动 Prompt 模板语法，不要求存量模板为上下文声明占位符。

## Decisions

### D1 工具描述以「版本」为准，工具级描述作为默认继承

`catalog.tool.description` 是人读的、不随版本变化的文案；`tool_version.spec.description` 是模型读的契约。语义属于版本，因为新增参数会改变语义。

- 快照装配同时写入 `spec.description`（缺省时从 `tool.description` 继承并写入快照，保证快照自解释），模型工具卡只读快照。
- **替代方案**：模型工具卡直接读 `tool.description`。否决原因：历史版本回放会读到后来修改过的描述，破坏「按快照执行」；且 Agent 版本对比看不出描述差异。

### D2 模型可见契约与调用契约分离，但只允许「注解级」覆盖

`spec.input_schema` 是平台校验与远端调用实际使用的契约；新增 `spec.model_schema` 承载模型可见版本（含 `description`、`format`、`examples`、`enum` 说明）。

- 平台在保存版本时校验：`model_schema` 与 `input_schema` 的**结构**必须等价——属性集合、类型、必填项、嵌套结构一致；允许差异仅限注解类关键字（`description`、`title`、`format`、`examples`、`default` 的可读说明）。
- 结构不等价即拒绝保存，避免「模型按 A 构造、平台按 B 校验」的错位。
- 远端探测得到 `input_schema` 后，控制台可一键补全为 `model_schema`，也可以在探测结果上直接编辑。
- **替代方案**：直接改 `input_schema` 加描述。否决原因：`input_schema` 同时是调用契约，加 `format` 会改变校验行为，可能让模型通过平台校验却在远端被拒（远端只接受某种格式），也可能相反。

### D3 失败分流在看守层，错误详情在适配层保留

`ToolResult` 增加两项：`details`（字段/原因列表）与 `recoverable`（可恢复标记）。分流发生在工具节点的循环内，而不是在适配层抛异常。

- 适配层负责把异常翻译成 `error_code + details + recoverable`，不再丢弃 `details`。
- 节点层按 `recoverable` 决定回灌或终止；`ok=False` 不再无条件终止执行。
- 可恢复集合采用**白名单**：`INPUT_INVALID`、`TOOL_TIMEOUT`、`TOOL_HTTP_ERROR`、`TOOL_MCP_ERROR`、`RESOURCE_UNAVAILABLE`。不在白名单内的（`HIGH_RISK_BLOCKED`、未授权、契约结构损坏）一律终止。
- **替代方案**：默认全部可恢复，仅黑名单终止。否决原因：新增错误码会静默变成可重试，放大 Token 与副作用风险；白名单让「可重试」成为一个显式决定。

### D4 回灌正文使用统一的失败信封

回灌给模型的工具消息正文使用固定结构，而不是把异常文案直接塞进字符串：

```
{"status":"error","recoverable":true,"code":"INPUT_INVALID",
 "message":"...","fields":[{"field":"arguments/start_date","reason":"..."}],
 "hint":"修正参数后可重新调用"}
```

业务终态使用同一信封的 `status":"no_data"` + `recoverable:false` + 明确文案。

- 统一信封让模型不必猜测「这是一段错误还是正常数据」，也让轨迹可聚合统计。
- `hint` 是可选的人话补充，不承载业务逻辑。

### D5 回灌受既有预算约束，并对「原地打转」短路

不新增独立的重试计数上限，直接复用 `budget.consume_step()`；同时在节点内记录本轮已失败的 `(tool_code, arguments_digest)`，相同组合第二次出现时不再调用工具，直接回灌一条终态说明。

- 理由：模型最常见的无效行为是「同一参数再试一次」，这种调用不可能得到不同结果，却会消耗一个步骤和一次外部请求。
- **替代方案**：只靠步骤预算。否决原因：一次多余的外部调用可能在写操作上产生副作用，也浪费一次模型回合。

### D6 运行时上下文在渲染之后注入，作为一条独立 system 消息

注入点在 `render_node` 末尾：`[渲染出的 system] + [上下文 system] + [history] + [其余消息]`。

- 独立消息而非拼进原 system：不改写用户模板内容，模板语义保持原样；多条 system 在主流 OpenAI 兼容接口中被接受，且与「每轮重渲染、不累积」的既有约束一致。
- 位置在 system 之后、history 之前：上下文属于本轮全局约束，不应排在历史之后被当成对话的一部分；靠前也利于前缀缓存稳定。
- **不写入会话历史**：注入消息只在本轮消息序列中，检查点持久化的仍是模板渲染结果与用户/助手消息，避免按轮次累积。
- **替代方案**：在渲染器里支持内建变量 `{{now}}`。否决原因：破坏「未声明占位符即报错」的闭合性，并且要求每个模板都写这个占位符，等于把平台职责推给模板作者。

### D7 上下文取值在 run 开始时固定

上下文在 run 开始时取一次，写入运行时状态，同一 run 内所有模型调用复用同一份取值。

- 理由：一次执行可能跨越时间边界（23:59 开始、00:01 结束），轮内取值漂移会让同一轮的工具参数自相矛盾。
- 跨轮执行重新取值，因此「明天」在两轮之间可以指向不同日期。

### D8 上下文项用白名单枚举，未知项拒绝保存

本期支持 `now`、`timezone`；值由服务端产生。声明写入快照并参与 `config_hash`，值不写入快照（否则每次发布摘要都变）。

- 声明变化改变摘要 → 版本对比能看出「这个版本开始依赖时间」。
- 值不入快照 → 回放时读到的是当前时间，而不是历史时刻。这是有意的：回放要复现行为，不是复现时空。

### D9 观测字段复用 `request_body`，新增独立计数列

`insight.llm_call` 增加 `tool_count` 列（记录对象已有该字段但未落库），完整工具卡摘要写入既有 `request_body` 的 `tools` 字段。

- 计数列用于聚合与筛选，正文用于逐次复核。
- 不新增 `tool_card` 表：工具卡是本次请求的一部分，天然属于请求正文。

## Risks / Trade-offs

- [回灌放大 Token 消耗] → 白名单限定可恢复错误、复用步骤预算、相同参数短路；在最坏情况下与现状同为预算耗尽，但多了两轮有信息量的尝试。
- [工具卡变大推高每次调用的输入 Token] → 参数描述只写「含义 + 格式 + 边界」，不写散文；描述建议长度在控制台提示，超过阈值给告警而不阻塞。
- [`model_schema` 与 `input_schema` 结构校验遗漏某个关键字] → 校验按「属性/类型/必填/嵌套结构」逐层比对，任何未知的结构差异一律拒绝，宁可误拒不放行。
- [上下文注入改变既有 Prompt 的前缀缓存命中率] → 上下文位于 system 之后的独立消息，模板前缀不变；同一 run 内取值固定，缓存仍可命中。
- [历史版本没有描述，回放行为与新版不一致] → 快照冻结，历史版本按原样执行；新版本才获得新语义。此差异在变更说明与版本对比中可见。
- [工具失败不再必然终止，可能让「本该失败」的调用被模型掩盖] → 不可恢复错误仍直接终止；可恢复失败必须在执行记录留痕，最终结果与轨迹都能看到中间失败。

## Migration Plan

1. 先落数据与记录（可空的 `tool_count` 列、`spec` 内新增可选字段），旧数据无需回填。
2. 再落契约装配与工具卡生成，新保存的工具版本才带描述与格式；历史版本行为不变。
3. 再落失败分流与回灌，切换时对既有 Agent 只影响「工具失败后的行为」，预算上限不变。
4. 最后落上下文声明与注入，未声明的版本完全不受影响。
5. 回滚策略：各步骤独立可回退。回退失败分流只需恢复「`ok=False` 即终止」；上下文注入可按声明关闭，存量版本未声明即无注入。

## Open Questions

- 工具卡中的参数描述是否需要支持多语言（面向不同 `locale` 的最终用户）。本期只做单语言，字段留出扩展位。
- 「平台提供当前时间是否必要」尚缺真实模型证据。计划用同一输入（例如「武汉明天天气怎么样」）
  对同一 Agent 的 `runtime_context = []` 与 `["now", "timezone"]` 两个版本各跑 5 次，记录：
  写入工具参数的日期、是否出现年份回退（如 2025）、是否需要模型澄清。判定标准：关闭声明时
  出现年份错误或格式错误的比例显著高于开启声明，则保留该能力为默认推荐项。
  当前测试环境使用确定性模型替身，只能验证链路（上下文到达模型、日期文本正确），
  无法观测模型行为差异，结果待有真实模型环境后回填。
