# Spec Delta

## Purpose

为后端定义一套可依赖的日志契约：每条日志都有固定字段与贯穿上下文的标识，模型、MCP 与执行流程的关键位置都留下可读证据，同时保证日志既能被容器采集、也能在本地落成文件，且不会把提示词正文或凭据带出去。

## ADDED Requirements

### Requirement: 结构化日志字段契约

系统 SHALL 以结构化形式输出每条日志，并固定包含 `timestamp`、`level`、`event`、`service`、`environment` 五个字段；`trace_id`、`request_id`、`tenant_id`、`run_id` 四个字段必须存在，无对应上下文时以空值呈现，不得缺键。`event` 使用点分命名表达事件类型（如 `llm.call`、`mcp.probe`），语义不得只依赖自由文本描述。

#### Scenario: 生产模式输出可被机器解析

- **WHEN** 以 JSON 输出模式启动服务并处理一次请求
- **THEN** 每行日志为单条 JSON 对象，且包含上述九个固定字段

#### Scenario: 开发模式不丢字段

- **WHEN** 以人类可读输出模式启动服务
- **THEN** 输出仍携带相同的字段集合，仅渲染形式不同

#### Scenario: 框架自身日志并入同一结构

- **WHEN** HTTP 服务器输出访问日志或第三方库输出告警
- **THEN** 这些记录与业务日志使用同一字段结构与同一输出通道，不出现第二种格式

### Requirement: 上下文标识贯穿日志

系统 SHALL 为每个受理的请求生成或沿用 `trace_id` 与 `request_id`，在认证成功后补充 `tenant_id`，并在进入一次 Agent 执行后补充 `run_id`；该请求内产生的所有日志都必须携带这些标识，响应头也必须回传 `trace_id` 与 `request_id`。后台异步进程 SHALL 在启动时标明自己的服务名，不继承任何请求级上下文。

#### Scenario: 一次请求内的日志可被串联

- **WHEN** 携带 `X-Trace-Id` 发起一次调用
- **THEN** 该请求产生的全部日志携带同一 `trace_id`，响应头回传同一个值

#### Scenario: 租户标识出现在认证之后的日志中

- **WHEN** 已认证用户触发一次需要落日志的操作
- **THEN** 该请求后续日志包含该用户的 `tenant_id`，且未认证请求的日志中该字段为空

#### Scenario: 执行日志带运行标识

- **WHEN** 一次 Agent 执行开始
- **THEN** 本次执行产生的模型调用、工具调用与节点日志都携带该次运行的 `run_id`

### Requirement: 关键执行位置产生日志事件

系统 SHALL 在以下位置产生日志事件，且事件包含足以在不查库的情况下判断成败与耗时的字段：

- 调用受理与收口：`run_id`、`agent_id`、`env`、`status`、`steps`、`tokens`、`latency_ms`、失败时的错误分类；
- 执行节点与路由决策：节点名、当前步数、下一步走向；
- 模型调用：模型名、工具数量、输入与输出 Token、耗时、成功与否及错误分类；
- 模型上游失败：归一后的错误分类与上游状态码；
- MCP 调用：目标主机与路径、传输方式、远端工具名、建连耗时、调用耗时、是否为错误响应；
- MCP 探测：目标主机与路径、发现的工具数量、耗时与结果。

#### Scenario: 模型调用成功留下证据

- **WHEN** 一次模型调用成功返回
- **THEN** 输出一条模型调用事件，包含模型名、Token 数与耗时，且不包含提示词或响应正文

#### Scenario: 模型上游失败可区分原因

- **WHEN** 模型调用因限流、超时或鉴权失败
- **THEN** 输出一条失败事件，包含与数据库轨迹一致错误分类与耗时

#### Scenario: MCP 调用能区分卡在建连还是调用

- **WHEN** 一次 MCP 工具调用超出预算或返回错误
- **THEN** 输出的事件分别给出建连耗时与调用耗时，并标明错误来源

#### Scenario: 执行流程可旁听

- **WHEN** 一次多步执行从渲染到模型再到工具循环
- **THEN** 每个节点进入与每次路由决策都产生对应级别的日志事件，且携带当前步数与 Token 用量

### Requirement: 日志双落地

系统 SHALL 始终把日志写入标准输出；当配置了日志文件路径时，SHALL 同时写入该文件，并在文件达到配置的大小上限时轮转、只保留配置数量的历史文件。API 服务进程与后台投递进程 SHALL 写入各自独立的文件，不得相互交错。未配置路径时 SHALL 不创建任何日志文件。

#### Scenario: 容器内运行只依赖标准输出

- **WHEN** 以容器方式启动且未配置文件路径
- **THEN** 全部日志出现在容器标准输出，容器内不产生日志文件

#### Scenario: 本地直跑留下可检索的文件

- **WHEN** 本地启动 API 服务并配置了日志文件路径
- **THEN** 日志同时出现在终端与该文件，文件超限后按序轮转

#### Scenario: 两个进程同时写日志

- **WHEN** API 服务与后台投递进程在同一台机器上运行
- **THEN** 两者分别写入不同文件，任一文件中不出现另一进程的交错内容

### Requirement: 敏感内容不进入日志

系统 SHALL 保证日志中不出现提示词正文、模型响应正文、工具参数原文、凭据原文、认证请求头以及 URL 的查询串与用户信息。需要体现参数特征时，只允许输出摘要或字符长度；需要体现目标地址时，只允许输出主机与路径。该约束在默认配置下生效，不因开启正文留存策略而放宽。

#### Scenario: 含敏感参数的工具调用

- **WHEN** 一次工具调用的参数包含被标记为敏感的字段
- **THEN** 日志中只出现该参数的摘要或长度，不出现原值

#### Scenario: 上游错误体含凭据

- **WHEN** 模型或 MCP 上游返回的错误内容包含凭据或请求头
- **THEN** 日志只记录归一后的错误分类与状态码，不转发上游错误体

### Requirement: 日志故障不影响业务

系统 SHALL 在日志渲染或写入失败时降级处理：请求与执行的结果、状态与响应内容保持不变，且失败本身最多产生一条告警。

#### Scenario: 日志目标不可写

- **WHEN** 配置的日志文件因权限或磁盘原因无法写入
- **THEN** 业务请求仍正常完成，服务输出一条关于日志降级的告警，不抛出错误
